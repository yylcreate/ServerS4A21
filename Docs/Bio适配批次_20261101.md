# 生化战场适配批次（2026-11-01）

本文记录当前项目把参考端“生化战场”接入 A21 服务端的分批边界。参考项目只提供行为线索；当前客户端协议以 `Server/DfoServer/Network/Core/PacketTypesA21.cs`、当前 PVF 和实机证据为准。

## 已确认的当前资源和协议名称

- 当前 PVF（通过显式 `PVF_ARCHIVE_PATH` 读取）包含 `etc/gamemode/zombiemode.etc`、`etc/MatchingMode.etc`、副本 3101 及生化地图/城镇/UI 资源。
- 当前 PVF 的匹配定义为频道模式、5～6 人、左右各 3 个席位；生化模式使用副本 3101，准备时间 5 秒，对局时间 300 秒。
- A21 枚举已经包含生化相关名称：`REQUEST_INTEGRATED_MATCHING`、`CANCEL_INTEGRATED_MATCHING`、`MATCHING_DUNGEON_EXIT`、`SELECT_ZOMBIE`、`TO_BE_ZOMBIE`、`ZOMBIE_MODE_RESULT_SCORE`，以及对应的生化通知名称。枚举只证明名称和 opcode 归类，不能证明 body 长度、包序或客户端消费条件。
- 当前 `channel_info.etc` 只有 `[zombie]` 的副本名称条目，没有可供当前服务端直接判定的生化 listener/server 行。因此专用频道、出生点和准入仍需部署配置与客户端证据，不能按参考端的端口或频道常量硬编码。

## 第一阶段：已实现的领域核心

本批次新增 `Server/DfoServer/Game/Dungeon/Bio`，只负责可独立验证的领域状态，不向客户端发包，也不写数据库：

- `BioDefinition` 将 PVF 的匹配人数、左右席位、准备/对局时间、感染者怪物、积分、奖励原始配置和禁用职业投影为不可变定义；缺字段或结构不合法时 fail-closed。
- `BioMatchingQueue` 以 session/account/character/user/listener 身份建立票据，防重复 owner；队列按 listener 隔离，冻结时校验票据仍然有效、人数在 PVF 范围内且席位不重复。
- `BioDungeonRuntime` 作为冻结队伍的共享 owner，绑定 `DungeonInstance` 与每个 `DungeonRun` 的 identity；阶段为 `Loading -> Ready -> Playing -> ResultPending -> Results -> Ended`。
- 进入、加载、身份选择、感染和计分均要求当前 session、character、user、run identity 与 generation 一致。重复进入/加载/感染/结算返回幂等结果；旧 generation、非成员或已结束实例被拒绝。
- `BioResultPlanner` 校验结果行数、席位唯一性、积分/生存时长上限和结果窗口，并按积分、生存时长、席位排序生成一次性结果事件。
- `DungeonInstanceMechanismRuntimeSet` 已为 Bio 预留唯一 runtime owner，并在实例结束时关闭 Bio runtime，避免另起第二套副本状态。

- 5 人队列、重复加入、冻结、取消旧票据和不同 listener 隔离；
- 5 名 active `DungeonRun` 的进入/加载、旧 generation 拒绝、身份选择、感染幂等、调用者不能伪造感染其他席位、计分排序、重复结算和实例结束后的拒绝；

## 尚未接入的后续阶段

1. `Network.Bio` typed parser/builder：按照当前 A21 抓包确认 request/cancel/select/transform/score/exit 的长度、字段和包序；参考端 body 不能直接复用。
2. 生化 listener 与频道准入：确认当前 channel catalog、listener type、20 级门槛、城镇 16 和断线清理策略；没有 server 行时保持匹配拒绝。
3. 生产 coordinator：把冻结 cohort 创建为 `DungeonInstance`/`DungeonRun`，接入 `DungeonMapHandler`、`DungeonLoadingCoordinator`、`DungeonRejoinCoordinator` 和 `ClockService` 的 generation/ticket fencing。
4. 结算和领取资格：复用当前 `InventoryLease`、`InventoryRewardGrantService`、`dungeon_persistent_effect_outbox` 与 `character_daily_counters`（计数键可为 `bio_completed_reward_games`），在同一 SQLite 事务中实现奖励幂等和失败重试；不复制参考端 MySQL schema。
5. `GameProtocolHandler` 注册和断线/Dispose 清理；补充协议 SelfTest、串行 `--selftest-all`，最后由用户用当前客户端实机验证 UI、包序、重连和奖励领取。

在这些阶段完成前，本批次只能称为“生化领域核心适配”，不能宣称客户端可直接游玩或奖励已闭环。
