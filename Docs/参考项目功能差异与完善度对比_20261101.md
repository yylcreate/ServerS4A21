## 3. 总体判断

当前项目和参考项目的优势不同：

| 维度 | 当前项目 | 参考项目 |
| --- | --- | --- |
| 游戏功能面 | 已覆盖拍卖、邮箱、库存、Dungeon、Raid、PVP、任务、好友、NPC 好感、专家职业、活动等主要路径；部分参考端活动和运营模块未见对应入口 | 功能目录更宽，额外包含多种活动、扫荡、Raid Auction、个人商店、Vending、里程商店、WebAdmin 和在线奖励等 |
| 数据 owner | SQLite 基线、typed migration、`InventoryLease`、`InventoryPersistenceService`、Repository/CommitService 边界较明确 | 大量旧代码直接使用 `MySqlConnection`/`MySqlCommand`；部分文件名虽含 `Sqlite`，内部仍是 MySQL 调用，迁移和业务边界耦合更重 |
| 协议接入 | `GameProtocolHandler` 分组注册，A21 命令从 `PacketTypesA21`、typed Parser/Builder 和组合根进入；当前金币寄售已补充专用分支 | handler 数量和协议面更宽，但存在旧命令、旧项目拆分和未能从当前客户端重新验证的字段；不能直接把旧 handler 当作 A21 真源 |
| 失败恢复 | 当前测试和实现普遍覆盖失败、回滚、旧 lease、session/generation、邮件幂等和刷新顺序 | 参考端有不少持久化和恢复代码，但没有当前项目这种集中、可串行执行的 SelfTest 证据 |
| 运营部署 | 当前运行面较轻，主要是服务端、SQLite、PVF 和协议自测 | 参考端含 IP 授权、WebAdmin、launcher、后台配置、在线奖励及多种运维/运营入口 |

因此，当前端的“工程化完善度”高于参考端，参考端的“功能覆盖面”宽于当前端。后续工作应把参考端额外功能视为移植候选，逐项补齐当前客户端抓包、PVF、`PacketTypesA21`、数据库 owner、事务和 SelfTest 证据后再决定是否接入。

## 6. 当前端相对参考端的新增或更完整部分

### 6.1 Guardian Altar

当前有完整的 `Game/Events/GuardianAltar`、Dungeon coordinator、Menu/Entry/Combat/Energy/Clear/Survival 相关模型和大量 SelfTest；当前 `GameProtocolHandler` 还注册了 Guardian Altar 入口和运行时命令。参考目录未发现同名 Guardian Altar 领域闭环。当前端已经把菜单持久化、房间/参与者、generation、奖励提交和返城投影拆开，后续仍需实机确认客户端动画、窗口和断线时序。

### 6.2 Epic Road、Scheduled Dungeon 和当前活动入口

当前有 `Game/Events/EpicRoad`、`EventDungeonOpening`、`ScheduledDungeons` 及对应组合根/自测。参考端存在旧的活动/副本代码，但没有同名的当前入口。应把这些视为当前端的新增实现，不要为了追求目录一致复制旧活动。

### 6.3 协议、事务和验证体系

当前 `GameProtocolHandler` 采用分组注册，覆盖登录、角色、库存、Dungeon、Quest、Mailbox、Auction、Party/Raid、Friends、Joust、NPC Favor、Guardian Altar 等入口；A21 名称和 opcode 由 `PacketTypesA21.cs` 提供。当前 `Network/Parsers`、`Builders`、`Game/*`、`Repository` 和 `SelfTests` 的职责边界更清楚。

当前 SelfTest 注册表包含 118 个参数，覆盖拍卖、邮箱、Inventory、Dungeon、Quest、活动、PVP、好友、NPC 好感、Guardian Altar 等成功/失败/回滚/旧 lease/generation 场景。参考 `Program.cs` 主要负责授权、启动、频道和时钟注册，没有同等集中可执行的 SelfTest registry；这说明当前端更容易进行串行回归和失败定位。

## 7. 数据库、运行和运营面的差异

### 7.1 数据库和事务

当前项目的真源是 `Server/DfoServer/Sqlite/item_schema.sql`、`Sqlite/SqliteMigrations.cs` 和 `GameDatabase`。在线 Inventory 要先取得当前 owned `InventoryLease`，变更沿 `InventoryPersistenceService`、Repository 或 CommitService 事务提交。当前 schema 版本和迁移会拒绝不匹配基线，SelfTest 覆盖新库、重复升级、拒绝和回滚。

参考端的 `DfoServer.MySql/MySqlMigrations.cs` 和大量 `MySql*Schema.cs` 说明它拥有更宽的持久化历史；但参考业务代码中可以看到 `MySqlConnection`、`MySqlTransaction`、`MySqlCommand` 直接进入 CharacterData、Inventory、Mailbox 等路径。即使文件名带有 `Sqlite`，如 `DfoServer.Game.CharacterData/SqliteSubtype0FieldsRepository.cs`，内部也出现 MySQL 调用。参考表不能直接迁移到当前 SQLite，也不能绕过当前 owned lease。

### 7.2 授权、后台和运营

参考 `Program.cs` 包含 IP 授权、`RuntimeAuthorization`、WebAdmin/launcher、后台配置、在线奖励和管理入口；参考根目录还有 `DfoServer.WebAdmin`、静态后台资源和授权公钥。当前项目没有同等的 WebAdmin/launcher/在线奖励后台闭环，启动面更轻，主要面向本地/服务端运行和 SelfTest。

这是运营能力差异，不应混入普通游戏协议完善度。若要补后台，必须单独设计权限、审计、账号/角色隔离和部署安全，不能复制参考端授权或后台代码直接进入当前服务端。

## 8. 结论和建议顺序

1. **先确定是否仍需要参考端扩展功能。** 优先确认 AbyssSweep、RaidAuction、PrivateStore、Vending、MileageShop、Harvest8Day、SandPass、EpicBurst/EpicWish、Bio 和 WebAdmin 的当前客户端入口与运营需求。
2. **每个候选功能先做证据包。** 至少包含当前 A21 抓包、`PacketTypesA21` 命令归类、PVF 配置、成功/失败包序、数据 owner、事务边界和断线/重连行为；没有证据的字段保留“待确认”。
3. **先补高价值、可闭环的业务。** 推荐顺序为 `RaidAuction`、`PrivateStore`、`AbyssSweep`、`Vending/MileageShop`，再评估活动和运营后台。每项单独建立 schema/迁移说明、SelfTest 和实机验收边界。
4. **不要按文件数追平参考端。** 当前端应继续保留 `InventoryLease`、typed Parser/Builder、session/generation fencing、统一事务和串行 SelfTest；参考端的旧 MySQL 表、直接 SQL、raw opcode 和后台授权逻辑不能直接复制。
5. **先核对 Wedding。** 当前工作树仅发现回放 builder，而参考端有完整 Wedding 业务。需要确认当前分支是否有另一套新命名实现；如果没有，应将 Wedding 作为独立批次，而不是把回放 builder 当作完整功能。
